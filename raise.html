Python raise

Até aqui, quem criava os erros era o Python: o int("dez") dava ValueError, o 10 / 0 dava ZeroDivisionError. Você só lia os erros e os tratava. Mas o seu próprio código também sabe quando algo está errado. Uma nota 15 numa escala de 0 a 10, um saque maior que o saldo, um desconto de 150%: o Python não acha nada de errado nesses números, mas você acha. Para avisar, existe o raise (em inglês, "levantar"): você lança um erro, exatamente como o Python lança os dele.

Você vai aprender
  • A lançar um erro com raise ValueError("mensagem") e a escrever uma boa mensagem.
  • Por que lançar um erro é melhor que dar um print e seguir em frente.
  • Que quem chama a sua função trata o seu erro com o mesmo try/except de sempre.
  • Qual tipo de erro escolher: ValueError, TypeError e outros.
  • O raise sozinho, que relança o erro, e o raise … from.
  • Os erros reais de quem está começando com o raise.

Todos os programas desta aula rodaram no Python 3.14 da máquina da Ana (usuária ana, computador notebook) com python3 arquivo.py. Para entender bem, vale ter visto Funções, return e try e except.

A ideia: levantar a mão

A Ana trabalha no caixa da padaria. Um cliente pede para pagar R$ 50 com uma nota de R$ 3. Não existe nota de 3 reais. O que ela faz?

  • Jeito errado: resmunga "nota estranha" baixinho e registra a venda mesmo assim. No fim do dia, o caixa não fecha, e ninguém sabe por quê.
  • Jeito certo: para tudo, levanta a mão e chama a gerente: "Problema aqui: nota de 3 reais não existe". A gerente decide o que fazer.

O raise é o "levantar a mão". Uma função que recebeu algo impossível não deve tentar seguir em frente nem só resmungar com um print: ela para e lança um erro com uma mensagem clara. Quem chamou a função (a "gerente") decide o que fazer: tratar com try/except ou deixar o programa parar.

3. Quem chama decide: try e except

O erro que você lança é um erro como outro qualquer. Quem chama a função pode tratá-lo com o try/except da aula try e except. Aqui, o programa pede a nota de novo até vir uma válida:

def validar_nota(nota):
    if nota < 0 or nota > 10:
        raise ValueError(f"A nota deve ficar entre 0 e 10, mas veio {nota}.")
    return nota


while True:
    try:
        nota = validar_nota(int(input("Nota: ")))
        break
    except ValueError as e:
        print(f"Erro: {e}")
print(f"Nota registrada: {nota}")

$ python3 pegar.py

Nota: dez

Nota: -1
Erro: A nota deve ficar entre 0 e 10, mas veio -1.
Nota: 8

Repare: o mesmo except ValueError pegou dois erros diferentes. O dez deu o ValueError do int(), com a mensagem do Python; o 15 e o -1 deram o ValueError da sua função, com a sua mensagem. Para quem trata, tanto faz quem lançou: o que importa é o tipo. É por isso que escolher o tipo certo é importante.

Divisão de trabalho

A função validar_nota não sabe o que fazer com uma nota ruim: num programa, o certo é perguntar de novo; noutro, pular o aluno; noutro, parar tudo. Por isso ela só lança o erro. Quem sabe o que fazer é quem chamou. Essa separação ("quem descobre o problema avisa; quem sabe resolver, resolve") é uma das ideias mais úteis da programação.

4. Qual tipo de erro lançar

Você pode lançar qualquer tipo de erro do Python, mas escolha o que descreve o problema, porque é pelo tipo que o except de quem chama vai reconhecê-lo. Os mais usados:

TipoQuando lançarExemplo
ValueErrorO tipo está certo, o valor não serveNota 15, desconto de 150%, quantidade negativa
TypeErrorVeio um tipo que a função não aceitaUm texto "50" onde devia vir um número
KeyError / IndexErrorProcurou algo que não existe numa coleçãoRaramente lançados à mão: o dicionário e a lista já lançam sozinhos
FileNotFoundErrorUm arquivo necessário não existeTambém costuma vir sozinho, do open()
Um erro seuNenhum dos de cima descreve bem o problemaSaldoInsuficiente: aula Criando suas Exceções

Um exemplo com os dois primeiros. O isinstance(preco, (int, float)) pergunta "o preco é um int ou um float?" e responde True ou False:

        raise TypeError(f"O preço tem de ser número, não {type(preco).__name__}.")
    if porcentagem < 0 or porcentagem > 100:
        raise ValueError(f"Desconto de {porcentagem}% não existe.")
    return preco * (1 - porcentagem / 100)


print(aplicar_desconto(50.0, 10))
print(aplicar_desconto("50", 10))

5. raise sozinho: relançar o erro

Às vezes você quer fazer alguma coisa quando o erro acontece (anotar, avisar) e, mesmo assim, deixar o erro seguir em frente, porque não é você quem sabe resolvê-lo. Dentro de um except, um raise sem nada depois relança o mesmo erro que acabou de ser pego:

def ler_preco(texto):
    try:
        return float(texto)
    except ValueError:
        print(f"[registro] preço mal digitado: {texto}")
        raise


print(ler_preco("4.50"))
print(ler_preco("4,50"))

Pega o erro do float(), que não entende a vírgula de 4,50.

Faz a anotação.

Sozinho, sem tipo: "lance de novo o erro que eu peguei". O erro continua sua viagem, como se o except não o tivesse segurado.

O traceback é o original: o erro aponta a linha 3, a do float(texto), e a mensagem é a do Python. Nada se perdeu; só se acrescentou o registro antes.

raise … from: trocar o erro por outro mais claro

Outro caso: o erro que aconteceu "por dentro" não faz sentido para quem usa a sua função. Um KeyError: 'café' diz pouco; "produto não cadastrado" diz tudo. Você pode lançar um erro novo e dizer que ele veio do antigo, com from ("de"):

precos = {"pão": 0.75, "leite": 5.49}


def preco_de(produto):
    try:
        return precos[produto]
    except KeyError as e:
        raise ValueError(f"Produto não cadastrado: {produto}") from e


print(preco_de("café"))

$ python3 from.py
Traceback (most recent call last):
  File "/home/ana/from.py", line 6, in preco_de
    return precos[produto]
           ~~~~~~^^^^^^^^^
KeyError: 'café'

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  File "/home/ana/from.py", line 11, in <module>
    print(preco_de("café"))
          ~~~~~~~~^^^^^^^^
  File "/home/ana/from.py", line 8, in preco_de
    raise ValueError(f"Produto não cadastrado: {produto}") from e
ValueError: Produto não cadastrado: café

Dois tracebacks, ligados pela frase do meio: "A exceção acima foi a causa direta da exceção a seguir." Embaixo, o erro novo (ValueError, com a sua mensagem); em cima, o erro original, guardado para quem quiser investigar. Compare com o "During handling of the above exception, another exception occurred" da aula try e except: aquele era um erro acidental dentro do except; este é uma troca de propósito.

TypeError: exceptions must derive from BaseException

"Exceções precisam derivar de BaseException." O raise só aceita erros (ValueError, TypeError…), e um texto não é um erro. Todos os tipos de erro do Python descendem de um "avô" comum chamado BaseException; é isso que a mensagem quer dizer. Ironia: tentando lançar o seu erro, você ganhou um TypeError. Como consertar: o texto vai dentro de um tipo de erro: raise ValueError("Idade negativa!").

Lançar o erro e tratar na mesma função

Um raise dentro de um try com except ValueError logo embaixo, na mesma função, é pego por ela mesma: o erro não chega a quem chamou. Em geral isso é sinal de confusão; se a própria função sabe resolver, ela não precisa lançar nada, basta um if. Lance na função que descobre o problema e trate em quem chama, como na seção 3.

Resumo

  • raise Tipo("mensagem") lança um erro, como o Python lança os dele: o programa para ali, a não ser que alguém trate.
  • Escreva mensagens que digam a regra e o valor que chegou: f"A nota deve ficar entre 0 e 10, mas veio {nota}.".
  • Lance em vez de dar print + return: assim o problema aparece na hora e no lugar certo, e não um None viajando pelo programa.
  • Quem chama trata com try/except; para o except, tanto faz se o erro veio do Python ou de você: vale o tipo.
  • ValueError para valor que não serve; TypeError para tipo errado. Tipos próprios: Criando suas Exceções.
  • raise sozinho, dentro de um except, relança o erro; raise Novo(…) from e troca por outro, guardando a causa.

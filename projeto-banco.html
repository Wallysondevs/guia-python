Python Projeto: Conta Bancária

O banco do bairro pediu à Ana um programinha para controlar as contas dos clientes: abrir conta, depositar, sacar, ver o extrato e, para quem tem poupança, render os juros no fim do mês. Neste projeto você vai construir esse programa quatro vezes, cada vez melhor. A primeira versão usa só o que você aprendeu no Nível 2 (dicionários e funções); as outras vão trazendo, uma por vez, as ferramentas da Orientação a Objetos. No fim, você vai ter visto na prática por que cada uma delas existe.

Neste projeto você vai usar
  • Dicionários e funções, na versão 1.
  • Classes e objetos, __init__ e self e métodos, na versão 2.
  • Encapsulamento, @property e raise, na versão 3.
  • Herança, polimorfismo, exceções próprias e try e except, na versão 4.

O que vamos construir

Esta é a versão final rodando no computador da Ana. A Ana tem uma conta corrente; a Bia, uma poupança. O programa faz alguns depósitos e saques (um deles sem saldo), fecha o mês e mostra o extrato de cada uma:

$ python3 banco.py
Bia: saque negado (saldo de R$ 1000.00, saque de R$ 2000.00)
  faltaram R$ 1000.00
--- ContaBancaria de Ana ---
Depósito     +100.00
Depósito      +50.00
Saque         -30.00
Saldo         120.00
--- ContaPoupanca de Bia ---
Depósito    +1000.00
Saque        -200.00
Juros          +8.00                « a poupança rendeu 1% no fim do mês
Saldo         808.00

As quatro versões:

  1. Dicionários e funções: funciona, mas os dados ficam soltos.
  2. Uma classe: dados e ações juntos, com extrato.
  3. @property e validação: o saldo só muda pelos métodos, e valores absurdos são recusados.
  4. Herança e uma exceção própria: a poupança e o SaldoInsuficienteError.

Antes de começar

Crie a pasta do projeto. O arquivo vai se chamar banco.py, e cada versão substitui a anterior:

$ mkdir -p projetos/banco
$ cd projetos/banco

Em cada versão há uma caixa Experimente, que roda Python de verdade aqui na página. As missões usam uma versão enxuta da conta, só com o que aquele passo precisa.

Versão 1 · Dicionários e funções

Com o que você já sabe, uma conta pode ser um dicionário com o titular e o saldo, e as operações podem ser funções que recebem a conta:

def criar_conta(titular, saldo=0):
    return {"titular": titular, "saldo": saldo}


def depositar(conta, valor):
    conta["saldo"] += valor


def sacar(conta, valor):
    if valor > conta["saldo"]:
        print(f"Saque de R$ {valor:.2f} negado: saldo insuficiente.")
    else:
        conta["saldo"] -= valor


def mostrar(conta):
    print(f"{conta['titular']}: R$ {conta['saldo']:.2f}")


ana = criar_conta("Ana", 100)
bia = criar_conta("Bia")

depositar(ana, 50)
sacar(ana, 30)
depositar(bia, 80)
sacar(bia, 200)

mostrar(ana)
mostrar(bia)
criar_conta(titular, saldo=0)
Monta e devolve o dicionário de uma conta. O saldo começa em 0 se ninguém disser nada.
conta["saldo"] += valor
As funções mudam o dicionário que receberam. Como dicionários são mutáveis, a mudança vale fora da função (aula Mutável × Imutável).
sacar(conta, valor)
A regra do banco: não se saca mais do que se tem.
conta['titular']
Dentro da f-string, aspas simples, porque a f-string já usa as duplas.
$ python3 banco.py
Saque de R$ 200.00 negado: saldo insuficiente.
Ana: R$ 120.00
Bia: R$ 80.00

Funciona. Mas repare em duas fraquezas. Os dados (o dicionário) e as ações (as funções) vivem separados: nada no dicionário diz que ele "sabe" sacar. E o dicionário aceita qualquer coisa, como você vai ver agora.

Versão 2 · Uma classe

Agora a conta vira uma classe. O que ela tem (titular, saldo, extrato) e o que ela faz (depositar, sacar, mostrar o extrato) ficam juntos:

class ContaBancaria:
    def __init__(self, titular, saldo=0):
        self.titular = titular
        self.saldo = saldo
        self.extrato = []

    def depositar(self, valor):
        self.saldo += valor
        self.extrato.append(f"Depósito: +{valor:.2f}")

    def sacar(self, valor):
        if valor > self.saldo:
            self.extrato.append(f"Saque negado: {valor:.2f}")
            return False
        self.saldo -= valor
        self.extrato.append(f"Saque: -{valor:.2f}")
        return True

    def mostrar_extrato(self):
        print(f"--- Extrato de {self.titular} ---")
        for linha in self.extrato:
            print(linha)
        print(f"Saldo: R$ {self.saldo:.2f}")


ana = ContaBancaria("Ana", 100)
bia = ContaBancaria("Bia")

ana.depositar(50)
ana.sacar(30)
bia.depositar(80)
if not bia.sacar(200):
    print("A Bia não conseguiu sacar R$ 200.00")

ana.mostrar_extrato()
bia.mostrar_extrato()
self.extrato = []
Cada conta nasce com a sua lista de movimentos, criada no __init__. (Na classe, fora do __init__, a lista seria uma só para todas as contas: veja Atributos e Métodos.)
self.extrato.append(…)
Todo depósito e todo saque deixam um registro. A lista guarda textos já formatados.
return False / return True
O sacar não imprime nada: ele responde se deu certo. Quem chamou decide o que fazer.
if not bia.sacar(200):
Chama o saque e, se ele devolveu False, avisa.

Compare a chamada: sacar(ana, 30) virou ana.sacar(30). A conta agora sabe sacar, e o nome saldo é escrito num lugar só (a classe), em vez de em cada função. Errar o nome de um atributo ainda dá erro, mas dentro de um arquivo só, perto de tudo o que a conta faz.

Versão 3 · @property e validação

Agora o saldo passa a morar em self._saldo (com sublinhado: "uso interno", aula Encapsulamento), e quem está de fora o enxerga por uma propriedade só de leitura (aula @property). Os métodos passam a recusar valores absurdos com ValueError:

class ContaBancaria:
    def __init__(self, titular, saldo=0):
        self.titular = titular
        self._saldo = 0
        self._extrato = []
        if saldo:
            self.depositar(saldo)

    @property
    def saldo(self):
        return self._saldo

    def depositar(self, valor):
        if valor <= 0:
            raise ValueError(f"depósito precisa ser maior que zero (veio {valor})")
        self._saldo += valor
        self._extrato.append(f"Depósito: +{valor:.2f}")

    def sacar(self, valor):
        if valor <= 0:
            raise ValueError(f"saque precisa ser maior que zero (veio {valor})")
        if valor > self._saldo:
            self._extrato.append(f"Saque negado: {valor:.2f}")
            return False
        self._saldo -= valor
        self._extrato.append(f"Saque: -{valor:.2f}")
        return True

    def mostrar_extrato(self):
        print(f"--- Extrato de {self.titular} ---")
        for linha in self._extrato:
            print(linha)
        print(f"Saldo: R$ {self.saldo:.2f}")

Por que não um setter com validação?

Daria para escrever um @saldo.setter que recusasse valores negativos (a missão final da aula @property faz isso). Aqui a escolha é outra: num banco, o saldo nunca é escrito direto; ele é o resultado de depósitos e saques, e cada um deixa registro. Sem setter, a única porta para mudar o saldo são os métodos.

Missão: o depositar desta conta aceita qualquer valor, e o depósito de -500 deixa o saldo negativo. Faça o método levantar um ValueError quando o valor for zero ou menos. O código de baixo já trata o erro: deve aparecer uma linha começando com Recusado: e, no fim, Saldo: R$ 150.00.

Versão 4 · Herança e uma exceção própria

Duas novidades. A primeira: o saque sem saldo vira uma exceção própria, SaldoInsuficienteError (aula Criando suas Exceções). Um return False é fácil de ignorar; uma exceção não. A segunda: a poupança vira uma classe filha da conta, que só acrescenta os juros (aula Herança).

class SaldoInsuficienteError(Exception):
    def __init__(self, saldo, valor):
        self.saldo = saldo
        self.valor = valor
        super().__init__(f"saldo de R$ {saldo:.2f}, saque de R$ {valor:.2f}")


class ContaBancaria:
    def __init__(self, titular, saldo=0):
        self.titular = titular
        self._saldo = 0
        self._extrato = []
        if saldo:
            self.depositar(saldo)

    @property
    def saldo(self):
        return self._saldo

    def _registrar(self, tipo, valor):
        self._extrato.append(f"{tipo:<10}{valor:>+10.2f}")

    def depositar(self, valor):
        if valor <= 0:
            raise ValueError(f"depósito precisa ser maior que zero (veio {valor})")
        self._saldo += valor
        self._registrar("Depósito", valor)

    def sacar(self, valor):
        if valor <= 0:
            raise ValueError(f"saque precisa ser maior que zero (veio {valor})")
        if valor > self._saldo:
            raise SaldoInsuficienteError(self._saldo, valor)
        self._saldo -= valor
        self._registrar("Saque", -valor)

    def fim_do_mes(self):
        pass

    def mostrar_extrato(self):
        print(f"--- {type(self).__name__} de {self.titular} ---")
        for linha in self._extrato:
            print(linha)
        print(f"{'Saldo':<10}{self.saldo:>10.2f}")


class ContaPoupanca(ContaBancaria):
    def __init__(self, titular, saldo=0, taxa=0.01):
        super().__init__(titular, saldo)
        self.taxa = taxa

    def fim_do_mes(self):
        rendimento = round(self._saldo * self.taxa, 2)
        if rendimento > 0:
            self._saldo += rendimento
            self._registrar("Juros", rendimento)

bia = ContaPoupanca("Bia", 1000)

ana.depositar(50)
for conta, valor in [(ana, 30), (bia, 2000), (bia, 200)]:
    try:
        conta.sacar(valor)
    except SaldoInsuficienteError as erro:
        print(f"{conta.titular}: saque negado ({erro})")
        print(f"  faltaram R$ {erro.valor - erro.saldo:.2f}")

for conta in [ana, bia]:
    conta.fim_do_mes()
    conta.mostrar_extrato()

As partes novas, uma por uma

class SaldoInsuficienteError(Exception):
Uma exceção é uma classe filha de Exception. O nome termina em Error, como as do Python (ValueError, KeyError): é o costume da PEP 8.
self.saldo = saldo / self.valor = valor
A exceção carrega dados: quem a captura sabe quanto havia e quanto foi pedido, e pode calcular quanto faltou.
super().__init__(f"saldo de R$ …")
A mensagem que aparece quando a exceção é mostrada (no print(erro) ou no traceback).
raise SaldoInsuficienteError(self._saldo, valor)
No lugar do return False. O saque não "responde que não deu": ele se recusa a terminar.
def _registrar(self, tipo, valor):
Um método interno (com sublinhado) que monta cada linha do extrato. O {tipo:<10} alinha o texto à esquerda em 10 colunas; o {valor:>+10.2f} alinha o número à direita em 10 colunas, com duas casas e sempre com sinal (+ ou -). Veja Formatação.
def fim_do_mes(self): pass
Na conta comum, o fim do mês não faz nada. O método existe para que toda conta tenha um fim_do_mes().
class ContaPoupanca(ContaBancaria):
A poupança herda tudo: depositar, sacar, extrato, a propriedade saldo. O __init__ dela chama o da mãe com super() e acrescenta a taxa.
def fim_do_mes(self): (na poupança)
Sobrescreve o da mãe: calcula os juros, arredondados em centavos com round(…, 2), e registra no extrato.
type(self).__name__
O nome da classe do objeto: ContaBancaria ou ContaPoupanca. O mesmo mostrar_extrato, herdado, mostra o tipo certo de cada conta.
for conta in [ana, bia]: conta.fim_do_mes()
Polimorfismo (aula Polimorfismo): o laço trata as duas contas igual, e cada uma faz o seu fim de mês.
$ python3 banco.py

Saque         -30.00
Saldo         120.00
--- ContaPoupanca de Bia ---

No fim do mês, a poupança rendeu 1% de 800, os R$ 8,00 de juros. A conta da Ana não rendeu nada: o fim_do_mes dela é o da mãe, que não faz nada.

Não existe uma versão "errada": a versão 1 é ótima para um script de dez linhas. O que muda é o tamanho do programa e quantas pessoas mexem nele. Quanto maior, mais vale a pena que o próprio código impeça os enganos, em vez de confiar que ninguém vai cometê-los.

Resumo

  • Versão 1: dicionário e funções funcionam, mas os dados ficam soltos e qualquer linha muda o saldo.
  • Versão 2: a classe junta dados e ações (ana.sacar(30)); cada conta tem o seu extrato, criado no __init__.
  • Versão 3: _saldo + @property sem setter deixam o saldo só de leitura; raise ValueError recusa valores absurdos; o saldo inicial entra como depósito.
  • Versão 4: SaldoInsuficienteError carrega o saldo e o valor; a ContaPoupanca herda tudo e sobrescreve só o fim_do_mes; um laço trata todas as contas igual (polimorfismo).
  • Cada ferramenta da Orientação a Objetos resolveu um problema que a versão anterior tinha de verdade.

Python Métodos Especiais

Você escreve print(5) e aparece 5. Escreve len("pão") e aparece 3. Escreve [1, 2] + [3] e aparece [1, 2, 3]. Mas experimente dar print num objeto da sua classe: sai um <__main__.Produto object at 0x7f…> que não diz nada. Os números, os textos e as listas sabem se mostrar, se comparar e se somar porque têm métodos especiais: métodos com nomes como __str__ e __eq__, que o Python chama sozinho na hora certa. Nesta aula, você vai dar esses poderes às suas classes.

Você vai aprender
  • O que são os métodos especiais (os "dunder") e quem chama cada um.
  • __str__: o que o print mostra.
  • __repr__: o que aparece dentro de uma lista e no modo interativo, e a diferença para o __str__.
  • __eq__: quando dois objetos são "iguais" para o ==.
  • __lt__: "menor que", para o sorted, o min e o max funcionarem.
  • __len__ e __add__: o len() e o + nos seus objetos.
  • Os erros reais: __str__ returned non-string, '<' not supported between instances, unhashable type, unsupported operand type(s) for +.

A ideia: o Python pergunta ao objeto

Pense numa tomada. Qualquer aparelho que tenha o plugue certo funciona nela: a geladeira, o liquidificador, o carregador. A tomada não sabe nada de liquidificadores; ela só exige o plugue.

O print, o len, o == e o + são tomadas. Quando você escreve len(x), o Python não sabe o que é x; ele procura em x o "plugue" chamado __len__ e o chama. Se o objeto tem o plugue, funciona. Se não tem, dá erro (ou, em alguns casos, o Python usa um comportamento padrão, sem graça).

Dá para ver o plugue das coisas que você já conhece:

texto = "lojinha"
print(len(texto))
print(texto.__len__())
print(3 + 4)
print((3).__add__(4))
print([1, 2] + [3])
print([1, 2].__add__([3]))

$ python3 por_dentro.py
7

[1, 2, 3]
[1, 2, 3]

len(texto) e texto.__len__() dão o mesmo resultado, porque o primeiro chama o segundo. O mesmo vale para 3 + 4 e (3).__add__(4). Você nunca vai escrever texto.__len__() no dia a dia (escreve len(texto), que é mais claro), mas agora sabe o que acontece por baixo.

Por que tantos sublinhados?

São dois sublinhados antes e dois depois: __len__. Em inglês, "double underscore" virou o apelido dunder; por isso muita gente fala "métodos dunder" (ou "métodos mágicos"). Os sublinhados avisam: "este nome é especial, o Python chama sozinho". Você já conhece um: o __init__, que o Python chama quando o objeto nasce (aula __init__ e self).

3. __repr__: o texto para quem programa

Com o __str__ pronto, a Ana pôs dois produtos numa lista e mandou mostrar a lista:

class Produto:
    def __init__(self, nome, preco):
        self.nome = nome
        self.preco = preco

    def __str__(self):
        return f"{self.nome}: R$ {self.preco:.2f}"


cesta = [Produto("Café", 18.9), Produto("Leite", 5.49)]
print(cesta)
print(cesta[0])

$ python3 lista_str.py
[<__main__.Produto object at 0x7fdd82990590>, <__main__.Produto object at 0x7fdd82978690>]
Café: R$ 18.90

O produto sozinho saiu bonito, mas dentro da lista voltou o endereço. É que uma lista, para se mostrar, não usa o __str__ de cada item: usa o __repr__ ("representação"). É o mesmo motivo pelo qual print(["Café"]) mostra ['Café'], com as aspas: dentro da lista, você vê cada item do jeito que ele seria escrito no código.

O costume é fazer o __repr__ devolver algo parecido com o código que cria o objeto:

class Produto:
    def __init__(self, nome, preco):
        self.nome = nome
        self.preco = preco

    def __str__(self):
        return f"{self.nome}: R$ {self.preco:.2f}"

    def __repr__(self):
        return f"Produto({self.nome!r}, {self.preco!r})"


cafe = Produto("Café", 18.9)
cesta = [cafe, Produto("Leite", 5.49)]
print(cafe)
print(repr(cafe))
print(cesta)
print(f"{cafe!r}")
def __repr__(self):
O método especial da representação. Também devolve um texto.
{self.nome!r}
O !r dentro da f-string pede o repr do valor, em vez do str. Para um texto, isso põe as aspas: 'Café'. Assim o resultado fica igual ao código Produto('Café', 18.9).
repr(cafe)
Chama o __repr__ diretamente.
f"{cafe!r}"
O mesmo !r, agora aplicado ao produto.
$ python3 com_repr.py

[Produto('Café', 18.9), Produto('Leite', 5.49)]

4. __eq__: quando dois objetos são iguais

A Ana cadastrou o café duas vezes, com o mesmo nome e o mesmo preço. Para ela, é o mesmo produto. Para o Python:

class Produto:
    def __init__(self, nome, preco):
        self.nome = nome
        self.preco = preco


a = Produto("Café", 18.9)
b = Produto("Café", 18.9)
print(a == b)
print(a == a)

$ python3 sem_eq.py
False
True

Sem __eq__, o == só responde True quando os dois lados são o mesmo objeto, igual ao is (aula is e in). O Python não sabe que, para a lojinha, o que conta é o nome e o preço. Você ensina com o __eq__ (de equal, "igual"):

class Produto:
    def __init__(self, nome, preco):
        self.nome = nome
        self.preco = preco

    def __eq__(self, outro):
        if not isinstance(outro, Produto):
            return NotImplemented
        return self.nome == outro.nome and self.preco == outro.preco


a = Produto("Café", 18.9)
b = Produto("Café", 18.9)
c = Produto("Café", 21.0)
print(a == b)
print(a is b)
print(a == c)
print(a != c)
print(a == "Café")
print(b in [c, a])
def __eq__(self, outro):
Recebe os dois lados do ==: em a == b, o self é a e o outro é b.
isinstance(outro, Produto)
"O outro lado é um Produto?" Se alguém comparar um produto com um texto, não faz sentido olhar outro.nome.
return NotImplemented
Um valor especial que quer dizer "não sei comparar com isso". O Python então tenta o outro lado e, se ninguém souber, responde False no ==. Repare: é return NotImplemented, um valor, e não um erro.
return self.nome == outro.nome and …
A regra da lojinha: mesmo nome e mesmo preço. Devolve True ou False.
$ python3 com_eq.py
True
False
False
True
False
True
  • a == b agora é True: mesmo nome, mesmo preço.
  • a is b continua False: são iguais, mas não são o mesmo objeto. O is não usa o __eq__.
  • a == c é False (preços diferentes), e o != deu True sem você escrever nada para ele: o Python usa o contrário do __eq__.
  • a == "Café" deu False, sem erro, graças ao NotImplemented.
  • O in também usa o ==: b está na lista porque é igual ao a que está lá.

5. __lt__: "menor que", para ordenar

A Ana quer a cesta ordenada do produto mais barato para o mais caro. Tenta o sorted (aula Ordenando Listas):

class Produto:
    def __init__(self, nome, preco):
        self.nome = nome
        self.preco = preco


cesta = [Produto("Café", 18.9), Produto("Leite", 5.49), Produto("Arroz", 27.5)]
print(sorted(cesta))

$ python3 sem_lt.py
Traceback (most recent call last):
  File "/home/ana/sem_lt.py", line 8, in <module>
    print(sorted(cesta))
          ~~~~~~^^^^^^^
TypeError: '<' not supported between instances of 'Produto' and 'Produto'

"O < não é suportado entre objetos Produto e Produto." Para ordenar, o sorted fica perguntando "este é menor que aquele?", com o <. E o Python não sabe o que é um produto ser "menor" que outro: mais barato? Nome antes no alfabeto? Quem decide é você, com o __lt__ (de less than, "menor que"):

class Produto:
    def __init__(self, nome, preco):
        self.nome = nome
        self.preco = preco

    def __repr__(self):
        return f"Produto({self.nome!r}, {self.preco!r})"

    def __lt__(self, outro):
        return self.preco < outro.preco


cafe = Produto("Café", 18.9)
leite = Produto("Leite", 5.49)
arroz = Produto("Arroz", 27.5)
cesta = [cafe, leite, arroz]
print(leite < cafe)
print(cafe > leite)
print(sorted(cesta))
print(sorted(cesta, reverse=True))
print(min(cesta))
print(max(cesta))
def __lt__(self, outro):
Em leite < cafe, o self é o leite e o outro é o café.
return self.preco < outro.preco
A regra: um produto é "menor" que outro quando é mais barato.
$ python3 com_lt.py
True
True
[Produto('Leite', 5.49), Produto('Café', 18.9), Produto('Arroz', 27.5)]
[Produto('Arroz', 27.5), Produto('Café', 18.9), Produto('Leite', 5.49)]
Produto('Leite', 5.49)
Produto('Arroz', 27.5)

Com um método só, funcionaram o <, o sorted (nos dois sentidos), o min e o max. E até o cafe > leite: o Python percebe que "café maior que leite" é o mesmo que "leite menor que café" e usa o __lt__ do leite. (O __repr__ está ali só para a lista sair legível.)

E o <=?

Esse não vem de graça: leite <= cafe dá o mesmo TypeError, agora com '<='. Cada comparação tem o seu método: __le__ (<=), __gt__ (>), __ge__ (>=). Para ordenar, o __lt__ basta. Se você precisar de todas, a próxima aula, Dataclasses, mostra o order=True, que escreve todas sozinho.

7. __add__: o + entre objetos

A Ana e a Bia vão juntar as compras num carrinho só. Com o __add__, isso vira um +:

class Carrinho:
    def __init__(self, itens=None):
        self.itens = list(itens) if itens else []

    def __len__(self):
        return len(self.itens)

    def __str__(self):
        return "Carrinho: " + ", ".join(self.itens)

    def __add__(self, outro):
        if not isinstance(outro, Carrinho):
            return NotImplemented
        return Carrinho(self.itens + outro.itens)


ana = Carrinho(["café", "leite"])
bia = Carrinho(["pão", "manteiga", "queijo"])
juntos = ana + bia
print(juntos)
print(len(juntos))
print(ana)
itens=None
O carrinho pode nascer vazio ou já com uma lista. (O None no lugar de [] é de propósito; o porquê está na aula Valores Padrão.)
", ".join(self.itens)
Junta os itens num texto, separados por vírgula e espaço.
def __add__(self, outro):
Chamado por ana + bia: o self é o carrinho da esquerda, o outro é o da direita.
return NotImplemented
Se o lado direito não for um carrinho, avisa "não sei somar isso", e o Python dá o erro certo (veja em Quando dá errado).
return Carrinho(self.itens + outro.itens)
Devolve um carrinho novo, com os itens dos dois. Os carrinhos originais não mudam, como em 3 + 4, que não muda nem o 3 nem o 4.
$ python3 add.py

Carrinho: café, leite

O carrinho juntado tem os 5 itens, e o da Ana continua com os dois dela.

Formas diferentes de fazer a mesma coisa

Para ordenar, existe outro caminho que não mexe na classe: o key= do sorted, que diz por qual valor ordenar (aula lambda):

class Produto:
    def __init__(self, nome, preco):
        self.nome = nome
        self.preco = preco

    def __repr__(self):
        return f"Produto({self.nome!r}, {self.preco!r})"


cesta = [Produto("Café", 18.9), Produto("Leite", 5.49), Produto("Arroz", 27.5)]
print(sorted(cesta, key=lambda p: p.preco))
print(sorted(cesta, key=lambda p: p.nome))

TypeError: cannot use 'Produto' as a set element (unhashable type: 'Produto')

"Não dá para usar Produto como elemento de um conjunto (tipo não hashable)." Conjuntos (aula Conjuntos) e chaves de dicionário precisam de um hash: um número de "etiqueta" que o Python calcula para achar o objeto depressa. Objetos iguais têm de ter a mesma etiqueta. Quando você escreve o seu __eq__, o Python não tem como saber qual etiqueta combina com a sua regra de igualdade e, por segurança, tira a etiqueta da classe.

Como consertar: se você precisa pôr os objetos num conjunto ou usá-los como chave, escreva também um __hash__ que use os mesmos dados do __eq__:

class Produto:
    def __init__(self, nome, preco):
        self.nome = nome
        self.preco = preco

    def __eq__(self, outro):
        return self.nome == outro.nome and self.preco == outro.preco

    def __hash__(self):
        return hash((self.nome, self.preco))


a = Produto("Café", 18.9)
b = Produto("Café", 18.9)
print(len({a, b}))

Resumo

  • Métodos especiais ("dunder") têm dois sublinhados de cada lado e são chamados pelo Python: o print chama o __str__, o len chama o __len__, o + chama o __add__.
  • __str__ é o texto para as pessoas (print, f-string); __repr__ é o texto para quem programa (listas, modo interativo). Sem __str__, o Python usa o __repr__; se for escrever um só, escreva o __repr__.
  • Os dois devolvem texto com return; um print no lugar dá __str__ returned non-string.
  • __eq__ decide o == (e, com ele, o != e o in). Com __eq__, escreva também __hash__ se o objeto for para um conjunto ou virar chave.
  • __lt__ basta para sorted, min e max. Para ordenar de vários jeitos, prefira key=.
  • Quando o outro lado não é do tipo esperado, devolva NotImplemented (um valor, não um erro).

Python venv

Na aula pip: Instalando Pacotes, o Ubuntu recusou o pip install e sugeriu "crie um ambiente virtual". Lá você usou três comandos sem muita explicação. Nesta aula você vai entender o que é esse ambiente virtual (em inglês, virtual environment, abreviado venv), o que tem dentro dele, como ligar e desligar, e por que todo projeto Python sério tem o seu.

Você vai aprender
  • O que é um ambiente virtual e por que cada projeto tem o seu.
  • A criar um com python3 -m venv .venv e a ver o que tem dentro da pasta.
  • A ativar (source .venv/bin/activate), reconhecer o prompt (.venv) e desativar (deactivate).
  • A conferir qual Python está em uso: which python e sys.prefix.
  • A apagar e recriar o ambiente a partir do requirements.txt.
  • Os erros reais: ativar sem source, pasta errada, copiar o projeto com a .venv junto.
Esta é uma aula de terminal

Ambientes virtuais são criados e ativados no terminal do seu computador. As janelas de terminal mostram o que o Ubuntu 26.04 da Ana respondeu de verdade. O editor do guia (o "Experimente") roda o Python do navegador, que não tem ambientes virtuais; as caixas desta aula treinam a lógica com os arquivos do ambiente.

A ideia: uma caixa de ferramentas para cada trabalho

A Ana faz bolos para fora e também conserta bicicletas no fim de semana. Ela não guarda as formas de bolo junto com as chaves de boca: cada atividade tem a sua caixa, com as ferramentas certas. Se um dia ela trocar a batedeira, a caixa da bicicleta nem fica sabendo.

Com os programas Python é igual. A lojinha da Ana usa o requests na versão mais nova; a agenda, que ela escreveu no ano passado, só funciona com uma versão mais antiga. Se os dois projetos usassem o mesmo Python, com os mesmos pacotes, um deles ia quebrar. A solução é dar a cada projeto a sua caixa:

Sem ambiente virtualCom um ambiente virtual por projeto
Todos os programas dividem os mesmos pacotesCada projeto tem os pacotes dele, numa pasta dele
Uma versão de cada pacote no computador inteiroA lojinha com o requests 2.34.2, a agenda com o 2.32.3, ao mesmo tempo
No Ubuntu, o pip install nem funciona (PEP 668)O pip funciona, sem sudo
Difícil saber do que o projeto precisaO pip freeze do ambiente é a lista exata

Um ambiente virtual é só isso: uma pasta com um Python "particular" e um lugar para os pacotes daquele projeto. Nada é instalado no sistema, e apagar a pasta desfaz tudo.

1. Criando: python3 -m venv .venv

A Ana vai começar um projeto novo, as encomendas da padaria. Primeiro a pasta do projeto, depois o ambiente dentro dela:

$ mkdir padaria
$ cd padaria
$ python3 -m venv .venv
$ ls -a

O Python que vai servir de base para o ambiente (o do sistema, o 3.14).
-m venv
"Rode o módulo venv": ele vem com o Python e sabe criar ambientes.
.venv
O nome da pasta do ambiente. Pode ser qualquer nome, mas .venv é o costume: os editores de código (como o VS Code) procuram por ele, e o ponto na frente deixa a pasta "escondida" no ls comum (por isso o -a, de "all", "todos").

2. Ativando: source .venv/bin/activate

Criar o ambiente não basta: o terminal continua usando o Python do sistema. Veja:

$ which python3
/usr/bin/python3
$ python3 -c "import sys; print(sys.prefix)"
/usr

which ("qual") mostra qual programa roda quando você digita um nome. E sys.prefix é a pasta "de casa" do Python que está rodando (o módulo sys tem aula própria: Os Módulos os e sys). Os dois apontam para o sistema. Agora a Ana ativa o ambiente:

$ source .venv/bin/activate
(.venv) ana@notebook:~/padaria$ which python3
/home/ana/padaria/.venv/bin/python3
(.venv) ana@notebook:~/padaria$ which python
/home/ana/padaria/.venv/bin/python
(.venv) ana@notebook:~/padaria$ python -c "import sys; print(sys.prefix)"
/home/ana/padaria/.venv
(.venv) ana@notebook:~/padaria$ pip list
Package Version
------- -------
pip     25.1.1
source
"Leia e execute este arquivo aqui, neste terminal". É obrigatório: o activate muda o terminal em que você está, e só o source deixa ele fazer isso.
.venv/bin/activate
O caminho do script, a partir da pasta do projeto.
(.venv)
O prompt ganhou o nome do ambiente na frente. É o sinal de que ele está ativo: olhe para ele sempre antes de rodar pip install.
which python3
Agora aponta para dentro da .venv.
pip list
Só o pip: o ambiente é novo e limpo.

O que o activate fez, por baixo, foi pôr a pasta .venv/bin na frente da lista de lugares onde o terminal procura os programas. Por isso python e pip agora são os do ambiente. Ele também criou a variável VIRTUAL_ENV, com o caminho do ambiente ativo (echo $VIRTUAL_ENV mostra).

Ativar vale só para aquele terminal

O ambiente fica ativo na janela (ou aba) de terminal em que você rodou o source, até você desativar ou fechar a janela. Abriu outro terminal? Ele começa com o ambiente desligado, e você ativa de novo. É normal rodar o source .venv/bin/activate toda vez que senta para trabalhar no projeto.

No Windows

A criação é igual (python -m venv .venv), mas a pasta se chama Scripts em vez de bin, e a ativação, no PowerShell, é .venv\Scripts\Activate.ps1. O resto da aula vale igual.

3. O próprio programa sabe se está num ambiente

Um programa Python consegue descobrir qual Python o está rodando. sys.executable é o caminho do Python em uso; sys.base_prefix é a pasta do Python original. Num ambiente virtual, sys.prefix (a pasta do ambiente) é diferente de sys.base_prefix:

import sys

print("Python em uso:", sys.executable)
print("Ambiente virtual?", sys.prefix != sys.base_prefix)

$ python3 onde.py
Python em uso: /usr/bin/python3
Ambiente virtual? False
$ source .venv/bin/activate
(.venv) ana@notebook:~/padaria$ python onde.py
Python em uso: /home/ana/padaria/.venv/bin/python
Ambiente virtual? True

O mesmo arquivo, dois resultados: o que muda é qual Python roda o programa.

Usar o ambiente sem ativar

Ativar é uma comodidade. Dá para chamar o Python do ambiente direto, pelo caminho, sem source nenhum. O resultado é o mesmo:

$ .venv/bin/python onde.py
Python em uso: /home/ana/padaria/.venv/bin/python
Ambiente virtual? True

É assim que se roda um programa de um projeto a partir de outro script ou de um agendador, onde ninguém vai digitar source. O mesmo vale para o pip: .venv/bin/pip install requests instala no ambiente, ativo ou não. E por que o .venv/bin/pip sabe para qual Python instalar? Porque a primeira linha dele diz:

$ cat .venv/bin/pip
#!/home/ana/padaria/.venv/bin/python3
# -*- coding: utf-8 -*-
import re
import sys
from pip._internal.cli.main import main
if __name__ == '__main__':
    sys.argv[0] = re.sub(r'(-script\.pyw|\.exe)?$', '', sys.argv[0])
    sys.exit(main())

O pip é um programinha Python, e a linha #! do começo (o "shebang") diz qual Python roda ele: o da .venv da padaria, com o caminho completo. Isso vai ser importante no Quando dá errado.

Missão: o pyvenv.cfg tem uma linha chave = valor por configuração. O programa já lê o arquivo; faça ele mostrar Este ambiente usa o Python 3.14.4, pegando o número da linha que começa com version. Dica: linha.split(" = ") separa a chave do valor.

with open("pyvenv.cfg", encoding="utf-8") as arquivo:
    for linha in arquivo:
        linha = linha.strip()
        print(linha)

home = /usr/bin
include-system-site-packages = false
version = 3.14.4
executable = /usr/bin/python3.14
command = /usr/bin/python3 -m venv /home/ana/padaria/.venv

with open("pyvenv.cfg", encoding="utf-8") as arquivo:
    for linha in arquivo:
        linha = linha.strip()
        chave, valor = linha.split(" = ")
        if chave == "version":
            print(f"Este ambiente usa o Python {valor}")

4. Desativando: deactivate

Terminou o trabalho no projeto? deactivate ("desativar") devolve o terminal ao normal. O (.venv) some do prompt, e o python sem 3 volta a não existir:

$ source .venv/bin/activate
(.venv) ana@notebook:~/padaria$ deactivate
$ which python
$ python --version
Comando 'python' não encontrado, você quis dizer:
  comando 'python3' do deb python3
  comando 'python' do deb python-is-python3

O which python não respondeu nada: não há programa com esse nome fora do ambiente. Desativar não apaga nada; o ambiente continua lá, com os pacotes, esperando o próximo source.

6. Apagar e recriar: o ambiente é descartável

Um ambiente virtual não guarda nada que você escreveu: o seu código fica fora dele, na pasta do projeto. Por isso ele é descartável. Estragou, ficou com pacotes demais, mudou de versão do Python? Apague e crie de novo. O requirements.txt (aula pip) traz os pacotes de volta:

$ cd loja
$ ls
baixar.py
requirements.txt
$ rm -rf .venv
$ python3 -m venv .venv
$ source .venv/bin/activate
(.venv) ana@notebook:~/loja$ pip install -q -r requirements.txt
(.venv) ana@notebook:~/loja$ pip list
Package            Version
------------------ ---------
certifi            2026.7.22
charset-normalizer 3.5.2
idna               3.20
pip                25.1.1
requests           2.34.2
urllib3            2.8.0
(.venv) ana@notebook:~/loja$ echo $VIRTUAL_ENV
/home/ana/loja/.venv
(.venv) ana@notebook:~/loja$ python baixar.py
Código: 200
Tipo: text/html; charset=utf-8
Tamanho: 577 caracteres

(O ls não mostra a .venv porque o nome começa com ponto.) Os mesmos pacotes, nas mesmas versões, e o programa funcionando. Essa é a rotina de quem recebe um projeto Python de outra pessoa: criar o ambiente, ativar, pip install -r requirements.txt.

rm -rf não tem volta

O rm -rf .venv apaga a pasta e tudo dentro, sem perguntar e sem lixeira. Confira o nome antes de apertar Enter: um espaço a mais (rm -rf . venv) apagaria a pasta atual inteira.

Quando dá errado

Rodar o activate sem o source 
$ .venv/bin/activate
bash: .venv/bin/activate: Permissão negada

Parece lógico chamar o script pelo caminho, como um programa. Mas o activate não tem permissão de execução, de propósito (repare no -rw-r--r-- dele no ls -l: nenhum x). Se ele rodasse como programa, mudaria um terminal "filho" que fecha logo em seguida, e o seu terminal continuaria igual. Como consertar: source .venv/bin/activate (ou a forma curta, . .venv/bin/activate, com um ponto e um espaço).

O caminho errado (ou a pasta errada) 
$ source venv/bin/activate
bash: venv/bin/activate: Arquivo ou diretório inexistente

A pasta se chama .venv, com ponto, e o comando pediu venv, sem. Muitos tutoriais usam venv ou env; o caminho tem de ser o da pasta que você criou. O mesmo erro aparece se você estiver em outra pasta: o caminho .venv/bin/activate é a partir de onde o terminal está. Como consertar: entre na pasta do projeto (cd ~/padaria) e confira o nome com ls -a.

deactivate sem ambiente ativo 
$ deactivate
deactivate: comando não encontrado

O deactivate só existe enquanto um ambiente está ativo: é o próprio activate que o cria. Sem (…) no prompt, não há o que desativar. Não é problema nenhum.

Esqueceu de dar o nome da pasta 
$ python3 -m venv
usage: python3 -m venv [-h] [--system-site-packages] [--symlinks | --copies]
                       [--clear] [--upgrade] [--without-pip] [--prompt PROMPT]
                       [--upgrade-deps] [--without-scm-ignore-files]
                       ENV_DIR [ENV_DIR ...]
python3 -m venv: error: the following arguments are required: ENV_DIR

"Os seguintes argumentos são obrigatórios: ENV_DIR" (environment directory, "pasta do ambiente"). A primeira parte é o resumo de uso: entre colchetes ficam as opções que você pode dar; ENV_DIR, sem colchetes, é o que você tem de dar. (Mensagens desse formato vêm do módulo argparse, que você vai usar para fazer os seus próprios programas de terminal na aula argparse.) Como consertar: python3 -m venv .venv.

Copiou o projeto com a .venv junto

A Ana quis fazer uma versão de teste da lojinha e copiou a pasta inteira. Ativou o ambiente da cópia e…

$ cp -r loja loja-copia
$ cd loja-copia
$ source .venv/bin/activate
(.venv) ana@notebook:~/loja-copia$ which python
/home/ana/loja/.venv/bin/python
(.venv) ana@notebook:~/loja-copia$ pip --version
pip 25.1.1 from /home/ana/loja/.venv/lib/python3.14/site-packages/pip (python 3.14)

Sem erro nenhum, mas olhe os caminhos: /home/ana/loja/.venv, e não loja-copia. O ambiente ativado foi o da pasta original. Um pip install agora mudaria a lojinha de verdade, e não a cópia de teste. O motivo: o ambiente guarda o caminho completo de onde foi criado (você viu no pyvenv.cfg e na primeira linha do pip), e o activate também:

$ grep -n "export VIRTUAL_ENV=" .venv/bin/activate
49:        export VIRTUAL_ENV=/home/ana/loja/.venv

Um ambiente virtual não se muda de lugar: nem copiando, nem renomeando a pasta do projeto. Como consertar: na cópia, apague a .venv copiada e crie outra (rm -rf .venv, python3 -m venv .venv, pip install -r requirements.txt). E, para mandar o projeto para alguém, mande o código e o requirements.txt, nunca a .venv.

The virtual environment was not created successfully because ensurepip is not available

Em alguns Ubuntu e Debian, o python3 -m venv falha com essa mensagem (ilustrativa: no computador da Ana o pacote já está instalado). O Ubuntu separa a criação de ambientes num pacote próprio. Como consertar: sudo apt install python3-venv e crie o ambiente de novo (apague antes a pasta que ficou pela metade).

Resumo

  • Um ambiente virtual é uma pasta (o costume é .venv) com um Python particular e os pacotes de um projeto.
  • Crie com python3 -m venv .venv, ative com source .venv/bin/activate, desative com deactivate.
  • Ativo, o prompt começa com (.venv), e python e pip são os do ambiente (which python confirma). Vale só para aquele terminal.
  • Sem ativar, chame pelo caminho: .venv/bin/python programa.py.
  • Cada projeto com o seu: dois projetos podem usar versões diferentes do mesmo pacote no mesmo computador.
  • O ambiente é descartável e preso ao lugar onde foi criado: não copie nem mova; apague e recrie com pip install -r requirements.txt.
